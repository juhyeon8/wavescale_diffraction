- 작성일: 2026-07-01
- 위치: `C:/dev/fourth-task`
- 베이스: 기존 [[2026-07-01-metal-bar-diffraction-design|금속 막대 회절 시뮬레이션 설계안]]에 이어지는 개선 작업
- 상태: **구현 완료** (최종값: `ZOOM_MIN=0.5`, `gridW=900`, 디바운스 150ms — §9)
- 목적: 구조물 크기와 파장의 상대 관계(λ/d, λ/H 등)에 따른 회절을 **여러 스케일에서

  않는 것이 핵심 요구사항이다.

## 0. 배경 / 문제 상황

기존(`script.js`의 `recompute()`)은 화면에 보이는 월드 좌표 범위(뷰)가
**오직 스크린 거리 L 값으로만 자동 계산**되었다.

```js
const xMax = L_m * 1.15;
const xMin = -Math.max(L_m * 0.4, 0.02);
```

그 결과 L을 조절하면 스크린 점선이 화면상 거의 같은 위치(~90% 지점)에
고정된 채 전체 배율만 확대·축소되는 것처럼 보였다. 사용자가 원하는 배율로
직접 확대·축소할 방법도 없었다.

---

## 1. 세 가지 범위(계층) — 이번 설계의 핵심

혼동을 피하기 위해 **월드 좌표 범위를 세 계층으로 명확히 분리**한다.

| 계층 | 이름 | 의존 대상 | 언제 바뀌나 | 용도 |
|---|---|---|---|---|
| ① 기준 범위 (줌 100%) | `base` (`baseXmin/baseXmax/baseYw`) | L 슬라이더의 **max 속성**(하드코딩 금지, DOM에서 읽음) + 레이아웃 aspect | 창 리사이즈(aspect 변경) 시에만 | 줌 배율 100%가 무엇을 의미하는지의 기준선. I(y) 곡선의 세로 범위도 여기서 고정 참조 |
| ② 물리 그리드 범위 | `gridWorld` (`gridWorld.xMin/xMax/Yw`) | `base` ÷ `ZOOM_MIN`(0.3) | N·d·a·λ·L 변경 시(recompute), 리사이즈 시 | 색지도 픽셀 배열(`incRe/incIm/scRe/scIm`)을 실제로 계산하는 세계 범위. **줌 배율과 무관** — 가장 넓은 줌아웃(0.3배)까지 미리 커버해둔다 |
| ③ 카메라(뷰) 범위 | `camera` (`camXmin/camXmax/camYw`) | `base` ÷ `view.zoomFactor` | 줌 버튼·휠 조작마다 | 화면(밴드)에 실제로 그려 보여주는 범위. `gridWorld` 범위의 부분집합이므로 항상 이미 계산된 데이터 안에서만 카메라가 움직인다 |

```
base.xmax   = L_MAX_m * 1.15
base.xmin   = -Math.max(L_MAX_m * 0.4, 0.02)
base.span   = base.xmax - base.xmin
base.Yw     = base.span * aspect / 2

gridWorld.xmax = base.xmax / ZOOM_MIN     // ZOOM_MIN = 0.3
gridWorld.xmin = base.xmin / ZOOM_MIN
gridWorld.Yw   = base.Yw   / ZOOM_MIN

camera.xmax = base.xmax / view.zoomFactor
camera.xmin = base.xmin / view.zoomFactor
camera.Yw   = base.Yw   / view.zoomFactor
```

`view.zoomFactor ∈ [0.3, 20]`이므로 `camera` 범위는 항상 `gridWorld` 범위
안에 포함된다 (zoomFactor=0.3일 때 camera == gridWorld, zoomFactor=20일 때
camera는 gridWorld의 아주 작은 부분).

이 분리 덕분에:
- **줌 조작은 `gridWorld`(물리 데이터)를 절대 건드리지 않는다** → recompute() 불필요.
- N·d·a·λ·L이 바뀌어도 `base`/`gridWorld`/`camera` 범위 자체는 안 바뀐다
  (막대가 범위보다 커지면 잘려 보이는 건 정상).

## 2. recompute() vs drawFrame() 역할 분리

- **`recompute()`** (무거운 MoM 솔버 + 픽셀별 베셀 합, 디바운스 60ms 유지):
  - `gridWorld` 범위(고정, N/d/a/λ/L과 무관)에서 오프스크린 격자(`incRe/incIm/scRe/scIm`)를 계산.
  - 트리거: **N·d·a·λ 변경**, 창 리사이즈(aspect 변경으로 `base`/`gridWorld` 재계산 필요).
  - **L 변경은 recompute를 트리거하지 않는다** — 아래 §2.1 참고.
  - **줌(버튼·휠)은 recompute를 절대 트리거하지 않는다.**
- **`drawFrame()`** (매 프레임/조작마다 가벼운 재렌더):
  - `camera` 범위를 계산 → `worldToBand()`가 이 범위를 기준으로 좌표 변환.
  - 오프스크린(고정 `gridWorld` 해상도)에서 `camera` 범위에 해당하는 **부분 사각형만
    `ctx.drawImage(offscreen, sx, sy, sW, sH, bandX, bandY, bandW, bandH)` 9-인자
    형태로 잘라서** 밴드 크기에 맞게 늘려 그린다. (기존엔 오프스크린 전체를 그대로 그렸음.)
  - 도선·스크린 점선·중심선 등 오버레이도 `camera` 범위 기준으로 그림.
  - 트리거: 애니메이션 루프, 줌 버튼/휠, 위상 슬라이더, **L 슬라이더**.

### 2.1 L 슬라이더는 recompute가 필요 없음 (구현 중 발견한 단순화)

기존 코드를 다시 보면 `recompute()` 안에서 `L_m`은 **뷰 범위 계산**에만
쓰였고(`xMax = L_m*1.15`), 실제 장(場) 값 계산(`evalFields`, 도선 유도전류
`solveComplex`)에는 전혀 쓰이지 않는다. 이번 설계에서 뷰 범위가 L과
완전히 분리되므로, **L은 이제 recompute()에 아무 영향도 주지 않는다.**
따라서:
- L 슬라이더는 `ampSlider`처럼 **`redrawOnly`로 바인딩** → `drawFrame()`만 호출.
- `drawFrame()` 안에서 스크린 점선 위치(`state.L_mm` 기반)와 오른쪽 I(y)
  곡선(`screenIntensity(L_m, wy)` 재계산, 그리드 재계산 아님)이 그때그때
  다시 그려진다.
- 체감상 L 슬라이더가 지금보다 더 즉각적으로 반응하게 되는, 순수한 개선.

## 3. 줌 상태 · 조작

- 뷰 전용 상태 `view = { zoomFactor: 1 }`를 물리 상태 `state`와 **분리된 객체**로 관리.
- 범위: **`ZOOM_MIN = 0.3` (30%, 최대 줌아웃) ~ `ZOOM_MAX = 20` (2000%, 최대 줌인)**,
  기본값 `zoomFactor = 1` (100%, L 최댓값까지 다 보이는 기준 범위).
  - 하한을 0.3까지 연 이유: 막대 높이 `H=(N−1)·d`가 커지면(큰 패러데이 케이지) 기준
    범위보다 훨씬 커질 수 있어, 케이지 전체와 파장의 관계를 보려면 통째로 조망하는
    줌아웃이 필요하기 때문.
- 항상 **도선 배열 중심(x=0, y=0) 기준**으로 확대·축소 (위 §1의 `camera` 공식이
  `base`를 원점 기준으로 나누기만 하므로 자동으로 만족됨).
- **UI**:
  - 패널에 **[−] / 배율%(예: `140%`) / [+] / [기본 보기]** 버튼.
    (배치 위치는 §6에 따라 미리보기 HTML로 먼저 확정.)
  - 캔버스(밴드 영역) 위 **마우스 휠**: 휠 업 = 확대, 휠 다운 = 축소, 한 틱당 대략 ×1.1,
    `wheel` 이벤트 `preventDefault()` 필요.
  - 버튼(×1.25 스텝)과 휠(×1.1/틱)은 **같은 `view.zoomFactor` 상태를 공유**, 동일한
    `[ZOOM_MIN, ZOOM_MAX]` clamp 적용.
  - "기본 보기" 버튼: `view.zoomFactor = 1`로 정확히 리셋.
- 줌인 상태에서 L을 크게 하면 스크린 점선이 `camera` 범위 밖으로 나갈 수 있음 →
  "기본 보기"로 복귀해서 다시 찾는다 (드래그 팬 기능 없음, 확정됨).

## 4. 격자 해상도

- 두 계층 분리로 인해 `gridWorld` 범위가 `base` 범위보다 **1/ZOOM_MIN ≈ 3.33배** 넓어짐.
  기존처럼 `layout.gridW = 360`을 그대로 두면 기본 보기(100%)에서 실제 보이는 폭에
  할당되는 픽셀이 약 108px로 줄어 지금보다 흐릿해지고, 줌인할수록 더 계단져 보인다.
- **잠정 결정(구판): `layout.gridW`를 1200px로 상향.** 실측 결과 성능 문제로
  **최종적으로 900px로 재조정됨 — §9 참고.** `gridH`는 기존처럼
  `Math.round(gridW * aspect)`로 비례 계산.
  - 트레이드오프: N·d·a·λ 변경 시(recompute, 디바운스 60ms) 격자 픽셀 수가
    가로·세로 모두 늘어나 총 계산량이 늘어난다(대략 (1/ZOOM_MIN)² ≈ 11배).
    N=120 등 무거운 설정에서 recompute 자체가 다소 느려질 수 있으나, **줌 조작은
    recompute를 아예 안 타므로 줌 자체의 반응성에는 영향 없음.**
  - 실제 체감 지연이 크면 추후 `gridW`를 낮추는 별도 조정을 고려한다(이번 범위 밖).

## 5. 오른쪽 세기 곡선 I(y) — 줌과 독립 (세로 범위는 `base.Yw` 고정)

- 기존 계획(§4, 구판)은 I(y) 곡선이 카메라(줌 반영) `Yw`를 세로 기준으로 쓰게
  되어 있었으나, 그러면 줌인 시 회절 무늬 봉우리들이 잘려 전체 패턴(중심 봉우리 +
  옆 봉우리들, 회절 차수)을 관찰하기 어렵다. **관찰 목적상 손실이므로 변경한다.**
- **결정: I(y) 곡선은 항상 `base.Yw`(고정 기준 범위, §1) 기준의 전체 스크린
  높이로 그린다.** `view.zoomFactor`가 무엇이든 이 곡선의 세로 샘플링 범위는
  바뀌지 않는다.
- 왼쪽 3개 밴드(카메라 범위 기준)와 세로 정렬이 어긋나는 시각적 대가는 감수한다(확정).
  곡선 패널에 **"전체 높이 기준"** 짧은 라벨을 붙여 정렬 차이를 명시한다.

### 8.1 성능 측정 결과 (2026-07-01, Playwright 헤드리스 크로뮴, N=120)

| gridW | gridH | recompute() 1회 |
|---|---|---|
| 360 (기존값) | 100 | **313 ms** |
| 600 | 167 | **909 ms** |
| **1200 (현재 구현값)** | 333 | **3536 ms (≈3.5초)** |

- gridW²에 거의 정확히 비례 (360→1200은 폭 3.33배, 시간은 11.3배 — 예상한 (1/ZOOM_MIN)²≈11.1배와 일치).
- **결론: gridW=1200은 N=120에서 λ/d/a 슬라이더를 만질 때마다 약 3.5초간 화면이
  멎는다.** 회절 관찰의 핵심 조작(파장·도선 파라미터를 바꿔가며 비교)이 정면으로
  막히므로, 목적에 비해 대가가 너무 크다고 판단된다. **사용자 확인 후 조정 필요**
  (§9, §4의 잠정 결정을 재검토).

## 9. 확정 조정 (2026-07-01, 사용자 지시) 및 재측정 결과

사용자 실사용 패턴(N 크게·d 작게, 큰 줌아웃은 거의 안 씀) 기준으로 아래 3가지를 확정 반영:

- **`ZOOM_MIN`: 0.3 → 0.5** (최대 줌아웃 30%→50%). §1 `gridWorld = base ÷ ZOOM_MIN` 공식,
  §3 값, §8 체크리스트의 "0.3배" 항목을 0.5 기준으로 갱신.
- **`gridW`: 1200 유지** — 줌인 선명도가 관찰의 핵심이라 하향 채택 안 함(§4의 (a) 미채택).
- **recompute 디바운스: 60ms → 150ms** — 드래그 중간 재계산을 줄여 슬라이더를 놓은 뒤
  한 번만 recompute 되게 함. §2 값 갱신.

### 9.1 재측정 — 중요한 정정: `ZOOM_MIN`은 recompute 성능에 영향이 없었다

당초 "`ZOOM_MIN` 0.3→0.5면 gridWorld 면적이 0.36배로 줄어 recompute도 0.36배(≈1270ms)로
줄 것"으로 추정했으나(§4/구판 §9), **실측 결과 사실이 아니었다**:

| 설정 (N=120, d=0.6mm) | recompute() 1회 |
|---|---|
| gridW=1200, ZOOM_MIN=0.3 (§8.1 원측정) | 3536 ms |
| **gridW=1200, ZOOM_MIN=0.5 (확정 반영 후)** | **3167~3231 ms — 사실상 동일, 개선 없음** |
| gridW=900, ZOOM_MIN=0.5 | 1659~1710 ms |

**원인**: `recompute()`의 격자 픽셀 수는 `gridW`(`layout.gridW`, 고정 상수)와
`gridH = round(gridW × aspect)`(레이아웃 종횡비, 고정)로만 정해지고, `gridWorld`가
실제로 덮는 **월드 공간 면적과는 무관**하다. `ZOOM_MIN`을 조절하면 그 픽셀들이
"얼마나 넓은 물리 영역을 대표하는지"(해상도)만 바뀔 뿐, **베셀 함수 평가 횟수
(=계산량)는 그대로**다. 즉 `ZOOM_MIN`은 성능 레버가 아니라 순수 **줌아웃 범위
설정값**이며, 계산 비용을 줄이려면 `gridW`(또는 `N`)를 낮추는 것만 유효하다.
이 정정을 반영해 §4의 "ZOOM_MIN 완화로 단축" 서술은 폐기한다.

### 9.2 gridW 최종 확정: 900

두 값 모두 "1초 이하 쾌적" 기준에는 못 미쳤으나:

- gridW=1200: 약 3.2초 — λ/d 슬라이더를 놓을 때마다 뚜렷하게 멎음.
- gridW=900: 약 1.6~2.0초 — 여전히 체감되지만 1200보다는 짧음.

**사용자가 900으로 최종 확정.** `layout.gridW = 900` 반영 완료, 전체 체크리스트(§8)
재확인 통과(N=120·d 작게 상태에서 λ 드래그 recompute ≈ 1999ms, 그 외 항목 전부
정상 — L/줌 recompute 0회, 리사이즈 후 zoomFactor 유지, 줌아웃 50%에서 큰 케이지
전부 보임, 콘솔 에러 없음).

## 11. 세로 범위(`baseYw`) — 파장·구조물 연동으로 재설계 (2026-07-01 후속)

### 11.1 문제

§1에서 확정한 `base.Yw = base.span × aspect / 2` 공식은 **가로 폭(L_MAX 기반)과
창 종횡비에서만 유도**돼, λ·N·d와 완전히 무관했다. 회절은 세로로 퍼지는
현상인데 세로 범위가 파장과 무관하게 고정되면, λ를 늘려도 회절 스크린샷들이
중앙의 얇은 띠 안에서만 변하고 화면상 변화가 거의 안 보인다.

### 11.2 진단 (물리 vs 시각화 스케일)

물리 함수(`besselJ0/Y0`, `hankel0`, `solveComplex`, `evalFields`,
`screenIntensity`)를 Node로 그대로 복사해 λ=12→25cm(N=40, d=4mm, L=80mm 고정)로
직접 계산해 확인:

| λ | 그림자 중심 I₀ |
|---|---|
| 12cm | 0.058 |
| 15cm | 0.064 |
| 18cm | 0.069 |
| 21cm | 0.073 |
| 25cm | 0.077 |

I₀가 λ에 꾸준히 반응(+33%)했고, y=0~200mm I(y) 프로파일에서도 그림자→투과
전환 구간이 λ가 클수록 더 넓고 완만해졌다. **결론: 물리/MoM은 정상, 원인은
시각화 스케일(세로 범위 고정) 확정** → 뷰 지오메트리만 수정.

### 11.3 공식 확정 — 합산 방식, `S=1.5`, `k=2`

```
H_m = (N − 1) × d_m          // 막대 전체 높이
lam_m = state.lam_cm / 100
baseYw = 1.5 × (H_m / 2 + 2 × lam_m)
```

원안이었던 `max` 방식(`S × max(H/2, k·λ)`, `S=2.5, k=3`)은 **폐기**했다.
λ 슬라이더 최댓값이 30cm까지 가는 반면 전형적인 `H/2`는 수십~200mm대라,
`3λ` 항이 `H/2`를 거의 항상 압도해서 막대가 뷰의 4~6%로 사라지는 문제가
있었다. `H/2`와 `k·λ`를 더하는 합산 방식으로 바꿔 막대 존재감과 회절
여유폭을 함께 확보했다.

5개 검증 케이스에서의 점유율(막대 높이 H / 뷰 전체 높이 2·baseYw):

| 케이스 | N | d(mm) | λ(cm) | H(mm) | baseYw(mm) | 막대 점유율 |
|---|---|---|---|---|---|---|
| A 기본값 | 40 | 4 | 12.2 | 156 | 483 | 16.1% |
| B λ 늘림 | 40 | 4 | 25 | 156 | 867 | 9.0% |
| C N큰·d작음 | 120 | 0.6 | 12.2 | 71.4 | 420 | 8.5% |
| D d 큼 | 40 | 10 | 12.2 | 390 | 659 | 29.6% |
| E 솔리드 | 40 | 4(a=2.5) | 12.2 | 156 | 483 | 16.1% |

막대 세부(도선 하나하나의 간격 등)를 더 크게 보고 싶을 때는 **줌인으로
보완**하는 설계로 확정(§3의 줌 기능은 그대로 유지).

### 11.4 반영 범위 — 가로 고정, 세로만 연동

- **가로(x) 범위는 그대로**: `baseXmax = L_MAX_M × 1.15`, `baseXmin =
  -max(L_MAX_M × 0.4, 0.02)` — 전파 방향이라 λ가 바뀌어도 고정돼야 좌우
  비교가 가능하다는 §1 원칙 유지.
- **세로(y) 범위만 위 11.3 공식으로 교체**. `computeBaseAndGrid()`가 매번
  `state.N`, `state.d_mm`, `state.lam_cm`를 직접 읽어 `baseYw`를 재계산한다
  (기존엔 `L_MAX` 상수 기반이라 state와 무관했음 — 이제 N/d/λ 변경 시
  `recompute()` 안에서 최신 state로 다시 계산됨. N/d/λ 슬라이더는 이미
  `scheduleRecompute()`에 바인딩돼 있어 별도 트리거 배선 변경은 불필요했다).
- `gridWorld.Yw = baseYw / ZOOM_MIN`, `camera.Yw = base.Yw / zoomFactor`는
  기존 공식 그대로 새 `baseYw`를 참조 — 계층 구조(§1) 변경 없음.
- `worldToBand()`, I(y) 곡선(`base.Yw` 참조, §5) 모두 별도 수정 없이 새
  `baseYw` 값을 그대로 사용해 정합됨.
- **알려진 트레이드오프**: `worldToBand()`는 x/y 범위를 밴드 폭/높이에 각각
  독립적으로 맞추므로(§1 이후 항상 그래왔음), x축과 y축의 "월드 미터당
  픽셀" 배율이 더는 같지 않을 수 있다(세로가 λ에 연동돼 가로와 다르게
  늘어나므로). 도선은 고정 반지름 원으로 그려 원 자체는 찌그러지지 않지만,
  인접 도선 간 세로 간격이 가로 거리와 "물리적으로 같은 비율"로는 안 보일
  수 있다 — 회절의 세로 퍼짐을 보여주기 위해 의도적으로 감수한 대가.

### 11.5 검증 결과 (Playwright 헤드리스 크로뮴, 2026-07-01)

- **λ 12→25cm (N=40, d=4, L=80 고정)**: ②산란파 밴드의 중심 로브가 좁고
  촘촘한 무늬(λ=12)에서 뚜렷이 넓은 무늬(λ=25)로 커짐을 스크린샷으로 확인.
  I(y) 곡선 형태도 함께 변화.
- **5개 케이스(A~E)**: 모두 막대와 회절 여백이 §11.3 표의 비율대로 화면에
  적절히 보임(스크린샷 확인).
- **§8 체크리스트 재확인**: 줌 버튼/휠·L 슬라이더는 `recompute()` 호출
  0회(콘솔 로그 카운트로 확인), N/d/λ 변경과 리사이즈는 각각 1회씩 정상
  트리거. 콘솔 에러 없음.
- 참고(범위 밖, 미수정): 정보 박스의 "L = …" 표시는 L 슬라이더 자체가 아닌
  다음 `recompute()` 때 갱신되는 기존 동작이 그대로 남아 있음 — 이번 세로
  범위 작업과 무관한 기존 동작이라 손대지 않음.

> **정정 (2026-07-01 같은 날 후속, §12 참고)**: 위 11.3 공식의 `2λ` 항은
> λ 비교 관찰 자체를 방해하는 부작용이 발견되어 **고정 마진으로 교체됐다.**
> 진단(11.2)과 원리(계층 구조, 가로 고정 등)는 그대로 유효하며, 세로 항의
> `λ` 의존성만 폐기됐다.

## 12. 세로 범위에서 λ 항 제거 — λ 비교 정확성 확보 (2026-07-01 재수정)

### 12.1 문제 — §11.3 공식이 λ 비교를 스스로 상쇄함

§11.3에서 확정한 `baseYw = 1.5 × (H/2 + 2λ)`는 세로 범위에 `λ`가 그대로
들어 있어서, λ를 늘리면 **회절이 실제로 더 퍼지는 동시에 화면 세로 범위
자체도 같이 커진다.** 두 효과가 반대 방향으로 상쇄돼 "λ가 길수록 회절이
더 퍼진다"는, 이 시뮬레이션의 핵심 관찰 목표가 화면에 잘 드러나지 않는
문제가 있었다. λ 비교가 목적이라면 세로 범위(측정 프레임)는 λ와 완전히
독립이어야 한다.

### 12.2 수정 — `λ` 항을 고정 마진으로 교체

```js
const Y_MARGIN_M = 0.10;   // 고정 세로 여백 100mm, λ와 무관. 헐겁거나
                            // 빡빡하면 이 상수만 조정.
baseYw = 1.5 × (H_m / 2 + Y_MARGIN_M)
```

- `H_m = (N − 1) × d_m`는 그대로 — 막대 가시성 유지를 위해 세로 범위는
  **막대 높이에는 계속 연동.**
- `Y_MARGIN_M = 0.10`(100mm)은 λ=6cm 부근에서 잘 보이던 비율(2λ=120mm)에
  근접하게 잡은 값. 상수를 파일 상단(`computeBaseAndGrid()` 바로 위)에
  명확한 이름으로 둬서 필요 시 값만 바꾸면 되게 했다.
- 가로(x) 범위는 이번에도 손대지 않음 — `baseXmax = L_MAX_M × 1.15`,
  `baseXmin = -max(L_MAX_M × 0.4, 0.02)` 그대로.
- `gridWorld.Yw = baseYw / ZOOM_MIN`, `camera.Yw = base.Yw / zoomFactor`,
  `worldToBand()`, I(y) 곡선(`base.Yw` 참조)은 모두 새 `baseYw`를 그대로
  참조하므로 추가 수정 없이 정합됨(§1 계층 구조 변경 없음).
- λ가 아주 커서(최대 30cm) 회절이 이 고정 프레임을 넘치면 **의도된 정상
  동작**으로 둔다 — 억지로 다 담으려고 세로를 λ 연동으로 되돌리지 않는다.
  넘칠 만큼 커진 것 자체가 회절 증가의 증거이며, 필요하면 줌아웃(§3)으로
  전체를 볼 수 있다.

### 12.3 찌그러짐(타원) — 이번엔 라벨로만 완화, 등방화는 보류

②산란파 밴드가 실제로는 동심원 파문인데 타원으로 보이는 이유는 가로
(전파거리, 수백 mm 스케일)와 세로(회절 스케일, 수십~수백 mm) 축척이
다르기 때문(§11.4에서 이미 알려진 트레이드오프). 이걸 1:1로 등방화하려면
스크린 L이 화면 밖으로 밀려나는 등 레이아웃 구조 자체를 바꿔야 해서, 이번
λ 비교 목표와 무관하게 작업 범위가 커진다. 이번엔 **②산란파 밴드 하단에
안내 라벨만 추가**해서 오해를 막는 선에서 마무리하고, 등방화는 별도
작업으로 보류한다.

```
if (band === 1) {
  ctx.fillText("실제로는 원형 파문 — 가로·세로 축척이 달라 타원으로 보임", ...);
}
```

### 12.4 검증 결과 (Playwright 헤드리스 크로뮴, 2026-07-01)

- **λ 12→18→25→30cm (N=40, d=4, L=80 고정)**: 세로 프레임(밴드 크기·막대가
  차지하는 픽셀 높이)이 완전히 고정된 채, ②산란파 밴드의 중심 로브만
  단조롭게 커지는 것을 스크린샷으로 확인. λ=30cm(슬라이더 최댓값)에서는
  로브가 밴드 세로 전체를 채우고 위아래로 살짝 넘치는 것까지 확인 —
  의도된 "프레임 초과 = 회절 증가의 증거" 동작.
- **줌아웃 대응**: λ=30cm 상태에서 줌아웃(−버튼 3회, 100%→51%) 시 넘쳤던
  패턴 전체가 화면 안에 들어옴을 확인.
- **N/d 변경 시 프레임 갱신**: N=100·d=8mm(H=792mm)로 바꾸면 막대와 회절
  패턴이 그에 맞게 큰 프레임으로 재조정됨을 확인 — 막대 가시성 유지 목적
  달성.
- **② 밴드 안내 라벨**: λ=12/18/25/30cm 전 구간 스크린샷에서 정상 표시 확인.
- **§8 체크리스트 재확인**: 줌 버튼/휠·L 슬라이더 → `recompute()` 0회,
  N/d/λ 변경·리사이즈 → 1회씩 정상 트리거(콘솔 로그 카운트로 확인). 콘솔
  에러 없음.
- 물리 함수(`besselJ0/Y0`, `hankel0`, `solveComplex`, `evalFields`,
  `screenIntensity`, MoM 구성)는 미변경 — `computeBaseAndGrid()`의 세로
  범위 계산과 `drawOverlay()`의 ② 밴드 라벨 추가만 수정됨.
