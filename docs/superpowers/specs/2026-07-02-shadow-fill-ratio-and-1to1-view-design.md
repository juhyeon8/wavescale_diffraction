# 금속 막대 회절 시뮬레이션 — 그림자 채움률 S̄ 지표 + 1:1 관찰 모드 설계

> 이 문서는 `docs/superpowers/specs/2026-07-01-zoom-and-view-design.md`(§1~§17)의 후속이다.
> 섹션 번호는 그 문서에 이어 §18부터 시작한다.

## 18. 배경과 목표

기존 구현(§13~§17)까지 완료된 상태: 도선 배열/솔리드 막대 모드, λ/H·Fresnel 수 배지,
H 치수선, 등방화된 3분할 뷰(하한 우선 시 축척비 소표기), I₀·어두운 구간 폭(I<0.5)
지표.

이번 작업의 목표 두 가지:

- **(A) 그림자 채움률 S̄** — "기하 그림자 영역에 회절로 흘러든 에너지"를 프레넬
  진동에 강건한 단일 지표로 정량화한다. 기존 I₀(중심 한 점)는 λ=2~4cm 근접장
  구간에서 값이 출렁이는 반면(§16 각주 참고), 구간 평균인 S̄는 이 진동에 덜
  민감할 것으로 기대된다.
- **(B) 1:1 관찰 모드** — 가로:세로 축척이 항상 정확히 1:1인 전체 화면 관찰
  모드를 추가해, 스크린 거리 L과 무관하게 회절 퍼짐각(θ≈λ/H)을 왜곡 없이
  관찰할 수 있게 한다. 3분할 뷰(§13)는 밴드 하나의 픽셀 종횡비가 작아
  H가 L에 비해 크면 등방이 구조적으로 깨지는 한계가 있었다(§13.3) — 1:1
  모드는 이 한계를 별도 관찰 모드로 우회한다.

**절대 변경 금지(물리 정확도 영역)는 기존과 동일**: `besselJ0`, `besselY0`,
`hankel0`, `solveComplex`, `evalFields`, `screenIntensity`, `recompute()` 안의
MoM 행렬 구성 로직, `colorFor`. 이번 작업 전부 지표 계산/뷰/레이아웃/UI 계층이다.

## 19. 그림자 채움률 S̄ 지표

### 19.1 정의

스크린(x=L)에서 기하 그림자 영역 `|y| ≤ H/2`에 대한 세기 평균(입사 세기=1 기준):

```
S̄ = (1/H) ∫ I(y, L) dy,   |y| ≤ H/2
```

기하광학이라면(회절 없이 빛이 직진한다면) 이 구간은 완전한 그림자이므로 S̄=0이어야
한다. 회절로 에너지가 흘러들수록 S̄가 커진다.

### 19.2 구현

```js
// H_m: 활성 모드 기준 막대 높이(barHeight_mm(state.N, state.d_mm)/1000) —
// 도선 모드든 솔리드 모드든 syncActivePhysics()가 이미 state.N/d_mm을
// 동기화해두므로 별도 모드 분기 불필요.
function computeShadowFillRatio(L_m, H_m, samples = 100) {
  let sum = 0;
  for (let s = 0; s < samples; s++) {
    const wy = -H_m / 2 + (s + 0.5) / samples * H_m;   // |y|≤H/2 균등 100점
    sum += screenIntensity(L_m, wy);
  }
  return sum / samples;
}
```

- 계산 위치는 `updateInfo()` 경로 전용(기존 `computeShadowProfile`의 120점 평가와
  같은 급의 비용 — `screenIntensity`는 이미 순수 포인트 평가라 `recompute()`의
  MoM/그리드 계산에는 영향 없음).
- `selfCheck()`는 실제 `screenIntensity` 의존 없이 순수 검증 가능하도록, 표본
  배열을 직접 받는 헬퍼(`shadowFillRatioFromSamples(samples: number[])`)로
  분리해 단언한다: **`S̄ ≥ 0`만 단언, 상한(S̄ ≤ 1)은 걸지 않는다.** 그림자
  경계 근처의 회절 무늬가 `|y|≤H/2` 구간 안으로 들어오면 국소적으로 입사
  세기(=1)를 넘는 지점이 있을 수 있고, 그 평균인 S̄도 1을 살짝 초과할 수
  있다 — 이는 버그가 아니라 정상적인 회절 간섭 현상이다.

### 19.3 표시

- 정보 박스 순서를 **S̄ → I₀ → 어두운 구간 폭**으로 재배열:
  `"그림자 채움률 S̄ = 0.xxx (기하광학이면 0)"`를 λ/H 다음 줄쯤 눈에 띄게 표시.
- I(y) 플롯에 기하 그림자 구간(`|y| < H/2`)을 파란 계열 옅은 음영
  (`rgba(47,111,235,0.10)`, 기존 accent색 재사용)으로 추가. 기존 I<0.5 음영
  (빨강, §16)과 겹치는 구간은 두 색이 자연히 섞여 보이며, 우측 하단에 소형
  범례 텍스트 한 줄로 "파랑=기하 그림자(|y|<H/2) · 빨강=어두운 구간(I<0.5)"을
  구분 표기한다.
- 힌트 문구(`index.html` 하단)에 한 문장 추가: "S̄는 기하광학이라면 0이어야 할
  그림자 영역에 회절로 흘러 들어온 에너지 비율로, 중심 한 점(I₀)과 달리
  프레넬 진동에 덜 흔들리는 판단 기준입니다."

## 20. 1:1 관찰 모드

### 20.1 핵심 통찰 — 물리 필드는 L과 무관하다

`evalFields(wx, wy, k, wiresY, cRe, cIm, aEff_m)`는 L을 인자로 받지 않는다.
전파하는 물리 필드 자체는 (x,y) 좌표만의 함수이며 L에 의존하지 않는다. L은
현재 3분할 뷰에서 "어디까지 그릴지"(뷰포트 범위)를 정하는 데만 쓰인다(§13.2).
이 통찰이 1:1 모드 설계 전체의 기반이다: **gridWorld(물리 필드가 실제로
계산된 세계 범위)를 충분히 넓게 잡아두면, L이 바뀌어도 이미 계산된 필드
안에서 크롭·크기만 다시 하면 되므로 재계산이 필요 없다.**

### 20.2 좌표계

```
Yw1to1  = 1.25 · (H/2 + 0.05)                          // L 무관, H만의 함수
xSpan1to1 = 2 · Yw1to1 · (bandW / bandH_1to1)          // 밴드 픽셀 종횡비로 역산
xMin1to1  = -xSpan1to1 / 3                              // 장애물(x=0)을 왼쪽 1/3 지점에 배치
xMax1to1  = 2 · xSpan1to1 / 3
```

`bandH_1to1 = cssH - marginT - marginB`(단일 밴드, gap 없음). `bandW`는
3분할과 동일(오른쪽 I(y) 플롯 열 폭 `plotW`는 두 모드 공통 유지).

이 정의상 1:1 모드는 항상 정확히 1:1 등방이다 — §13의 "하한이 등방을 이기는"
문제가 원천적으로 발생하지 않는다(축척비 배지도 뜨지 않음).

### 20.3 gridWorld 공유 — 두 모드 요구치의 합집합

```
gridWorld.xMin = min(baseXmin, xMin1to1) / ZOOM_MIN
gridWorld.xMax = max(baseXmax, xMax1to1) / ZOOM_MIN
gridWorld.Yw   = max(baseYw,   Yw1to1)   / ZOOM_MIN
```

`computeBaseAndGrid()`가 매 `recompute()`마다 3분할 몫(L 기반, 기존 §13.2)과
1:1 몫(H 기반)을 함께 계산해 이 합집합을 잡는다. `camera`(3분할용)와
`camera1to1`을 각각 `base`/`base1to1`을 `view.zoomFactor`로 나눠 산출한다 —
줌 배율은 두 모드가 공유하므로 1:1은 줌 인/아웃 시에도 항상 정확히 1:1을
유지한다.

**결과**: `recompute()`는 지금처럼 N/d/a/λ/L이 바뀔 때만 실행되고(기존과
동일), **모드 전환 자체는 gridH 요구치가 실제로 달라질 때만 recompute를
유발한다** — 아래 20.4 참고.

### 20.4 gridH 해상도 — 현재 모드 추종

3분할 밴드는 세로로 짧아(전체 높이의 1/3) `gridH`가 작아도(현재 기본값 기준
약 227행, recompute ~1~2초) 충분하지만, 1:1 모드는 밴드 하나가 전체 높이를
다 쓰므로 세로로 약 3배 더 길쭉해 같은 방식으로 잡으면 `gridH≈675`가 필요하다
(recompute ~3~6초로 증가).

**결정(사용자 확인, 수정)**: `gridH`는 **현재 활성 모드가 요구하는 값을
그대로 추종**한다 — 3분할이면 작게(≈227), 1:1이면 크게(≈675). 모드 전환
버튼을 눌렀을 때 요구 gridH가 지금 값과 다르면 그 즉시 1회 recompute(전환당
최대 1회)로 다시 맞추고, 같지 않으면(요구치가 동일하면) recompute 없이
`drawFrame()`만 호출한다. **1:1→3분할로 되돌아갈 때도 recompute를 허용한다**
(작은 그리드로 줄어드는 재계산이라 ~1~2초로 저렴하다) — 1:1 모드를 한 번
켰다는 이유로 이후 3분할 뷰의 모든 recompute가 3~6초로 눌러앉는 상태를
만들지 않기 위함이다. 같은 모드 안에서의 줌 조작이나(1:1에서의) L 조작은
gridH 요구치를 바꾸지 않으므로 recompute를 유발하지 않는다.

> **후속 옵션(이번 작업 범위 밖, 구현하지 말 것)**: 1:1 모드 recompute
> (3~6초)가 실사용에서 답답하면 1:1 모드에 한해 `gridW` 900→600 절충을
> 검토할 수 있다(계산 비용 레버는 `gridW × gridH × N`).

### 20.5 렌더링 분기

- `state.viewMode`: `'3band'`(기본) | `'1to1'`.
- `state.viewField`: `'inc'|'sc'|'total'` — 1:1 모드 전용, 기본 `'total'`(③중첩).
- `drawFrame()`이 `viewMode`로 분기: 3분할은 기존 3밴드 루프 그대로, 1:1은
  단일 밴드에 `viewField`가 가리키는 필드 하나만 크롭·렌더.
- `drawOverlay()`도 모드 인지: 1:1은 정의상 항상 등방이므로 축척비 배지는
  절대 뜨지 않는다. H 치수선·도선·진행 화살표는 1:1에서도 동일하게 표시한다.
- **스크린 점선**: `Lx ≤ camera1to1.xMax`면 기존처럼 세로 점선 표시. 초과 시
  (L 슬라이더 범위는 항상 10~300mm 양수이고 `xMin1to1`은 항상 음수이므로
  왼쪽 이탈은 발생하지 않는다) 우측 가장자리에 "스크린 → 오른쪽 밖 xxx mm"
  텍스트만 표시하고 뷰를 늘리지 않는다.
- `drawIntensityPlot(by, bh)`을 인자화해 3분할의 ③밴드 행이든 1:1의 단일
  밴드든 같은 함수로 그린다 — S̄·I₀·어두운 구간 폭 계산 로직은 완전히 공유
  (모드 무관, 현재 L·H만 반영하는 순수 평가이므로).

### 20.6 L 슬라이더의 모드별 동작

- `viewMode==='3band'`: 기존과 동일하게 `scheduleRecompute()`(§13.2, 디바운스
  150ms) — 가로 범위가 L에 종속되므로.
- `viewMode==='1to1'`: gridWorld가 이미 H 기반으로 충분히 잡혀 있어(20.3) L
  변경이 물리 재계산을 요구하지 않는다. `drawFrame()`만 호출 — 스크린 점선
  위치/라벨, I(y) 플롯, S̄/I₀/어두운 구간 폭(모두 `screenIntensity`의 순수
  포인트 재평가)만 즉시 갱신되고, 화면의 회절 무늬 자체는 전혀 바뀌지 않는다.
  **이것이 이번 작업의 핵심 검증 시나리오다(§22.3).**

### 20.7 UI

- "화면 보기 (줌)" 섹션 맨 위에 `.segbtns`(기존 스타일 재사용) 2버튼 토글:
  `[3분할 뷰(기본)] / [1:1 관찰 모드]`.
- 1:1 모드 활성 시에만 그 아래 표시 필드 선택 `.segbtns`(① 입사 / ② 산란 /
  ③ 중첩, 기본 ③) — `wireControls`/`solidControls`의 display 토글과 동일한
  패턴으로 숨김/표시.
- 줌 버튼·휠·"기본 보기" 리셋은 두 모드에서 공유(`view.zoomFactor` 단일 상태).
- 새 CSS 불필요.

## 22. 검증 계획

### 22.1 selfCheck() 신규 단언

- `shadowFillRatioFromSamples`류 순수 헬퍼: `S̄ ≥ 0`만 단언(상한 없음, §19.2).
- `Yw1to1` 공식 단언: 예) H=150mm → `1.25·(0.075+0.05) = 0.15625m`.
- gridWorld 합집합 계산을 담당하는 순수 함수: 3분할 몫과 1:1 몫 중 큰 쪽이
  선택되는지 대표값(예: H가 작아 3분할 몫이 이기는 경우/H가 커 1:1 몫이
  이기는 경우 둘 다)으로 단언.

### 22.2 λ 스윕 — S̄의 프레넬 진동 강건성 확인

솔리드 모드, H=150mm·L=100mm 고정, λ=2/8/24cm 지점에서 (임시 Playwright
스크립트로) λ, N_F, I₀, S̄, 어두운 구간 폭을 표로 출력해 확인:
- S̄가 세 지점에서 단조 증가.
- λ=2~4cm 근접장 구간에서 I₀ 대비 S̄의 출렁임이 크게 완화됨(15점 정도 세밀
  스윕으로 확인).

### 22.3 1:1 모드 핵심 검증 — L 변경 시 화면 불변

1:1 모드에서 L 슬라이더를 10→300mm로 이동해도 화면의 회절 무늬가 전혀
변하지 않아야 한다(스크린샷 비교) — 스크린 점선/라벨과 I(y)·S̄·I₀만 갱신.
이 구간에서 `[성능] recompute()` 콘솔 로그가 찍히지 않는지 확인한다.

### 22.4 회귀 확인

- 3분할 뷰로 되돌렸을 때 기존 동작 100% 회귀(축척비 소표기 포함).
- 도선 모드 λ/d 닿음·투과 배지 등 기존 배지 정상 동작.
- selfCheck() 단언 전부 통과, 페이지 에러 0건.
- **모드 전환은 gridH 요구치가 달라질 때만 recompute(전환당 최대 1회,
  양방향 모두 허용 — 1:1→3분할 복귀도 포함). 같은 모드 안의 줌 조작·
  (1:1에서의) L 조작은 recompute를 유발하지 않는다.** 콘솔의
  `[성능] recompute()` 로그로 확인한다(§20.4).

## 23. Self-Review 메모

- 절대 변경 금지 함수 목록 — 이번 작업 어디에서도 건드리지 않는다(§18).
- S̄와 1:1 모드는 서로 독립적이지만, 정보 박스·I(y) 플롯을 공유하므로 하나의
  설계서로 함께 정리했다(사용자 확인). 구현은 S̄ 먼저(위험도 낮음) → 1:1
  모드(뷰 아키텍처 변경, 위험도 높음) 순으로 Task를 나눈다.
- gridH 해상도 트레이드오프는 사용자에게 명시적으로 확인받은 결정이다(§20.4)
  — "현재 모드 추종"(모드 전환 시 요구치가 달라지면 그때만, 양방향으로
  최대 1회 recompute)을 선택했다. 1:1 모드가 자주 답답하면 후속으로
  `gridW` 축소를 검토할 수 있으나 이번 작업 범위 밖이다.

## 24. MoM vs 하위헌스 비교 페이지 — 배경과 목표

> 이 섹션(§24~)은 별개 작업이다. §18~§23(S̄ 지표 + 1:1 관찰 모드)은 완료되어
> `master`에 병합됐고, 이 섹션은 그 결과물(금속 막대 앱)과 기존 `huygens/`
> 앱을 **읽기 전용으로** 참조하는 신규 3번째 페이지를 다룬다.

**목표**: 금속 막대(EFIE-MoM, 엄밀해)와 하위헌스(프레넬 적분, 키르히호프
근사)가 같은 회절 물리를 구현함을 스크린 세기 곡선 I(y)로 정량 비교한다.
이론 관계: 하위헌스의 장애물 판은 키르히호프 근사, 금속 막대는 유한 도선
배열의 엄밀 산란해(MoM)다. 전방 영역에서는 물리광학 근사로 두 결과가
연결된다.

**절대 변경 금지(읽기 전용)**: `index.html`/`script.js`/`style.css`,
`huygens/` 하위 전체. 이번 작업은 신규 파일 `compare.html`/`compare.js`만
만든다.

## 25. 물리 코어 이식

### 25.1 금속 막대 쪽 (출처: `script.js`)

`besselJ0`, `besselY0`, `hankel0`, `solveComplex` — 문자 그대로 복사, 파일
상단에 `// 출처: script.js`로 명기.

MoM 구성도 `recompute()`(script.js:193~257)와 동일한 로직을 그대로 재현한다:
도선 위치 `wiresY[n] = (n-(N-1)/2)·d`, `Z_mn = H0(k|y_m-y_n|)`(자기항은
`H0(k·a)`), `b = -1`, `solveComplex`로 계수 `c_n` 산출. 스크린 세기는
`evalFields`/`screenIntensity`(script.js:128~148)와 동일하게
`|e^{ikL} + Σ c_n·H0(k·r_n)|²`(입사 세기=1 기준)이지만, 비교 페이지는 2D
필드 그리드 전체를 계산하지 않고 **스크린 곡선(y 표본점들)만** 평가하므로
`evalFields`를 그리드 루프가 아니라 y 배열 루프로 감싸는 얇은 래퍼로
재구성한다(계산 결과는 origin과 동일, 루프 대상만 다름).

### 25.2 하위헌스 쪽 (출처: `huygens/script.js`)

`fresnelCS`, `totalAmplitude` — 문자 그대로 복사, `// 출처: huygens/script.js`
명기. 세기는 `fresnelIntensity(Y, lambda, a, zDist, true)`를 그대로 쓰되
`REF_INTENSITY=2`로 나눠 입사=1 기준으로 정규화(huygens 원본과 동일한
정규화 방식). `a` 인자에는 비교 페이지의 `H`(전체 폭, mm→m 환산)를 그대로
전달한다 — `state.H_mm`이 금속 막대 쪽 솔리드 모드의 "장애물 높이 H"와
동일하게 "막대가 차지하는 전체 폭"이라는 점(script.js의
`computeSolidWireLayout(H_mm)`이 도선을 `-H/2~+H/2`에 배치)이 이미
확인됐으므로, 두 모형의 `H`/`a`는 기하학적으로 같은 양이다.

## 26. 이산화 전략

### 26.1 목표 간격과 상한

비교 페이지는 2D 색지도를 그리지 않고 스크린 곡선(241점)만 계산하므로
기존 앱(N 상한 120)보다 훨씬 높은 N을 쓸 수 있다:

```
d_target = min(1mm, λ/20)
N = min(400, ceil(H/d_target) + 1)
d = H/(N-1)          // N 확정 후 실제 간격 역산
a = d/2              // 도선 반지름(닿음, 솔리드 근사)
```

**정정(구현 후 §28.1 검증에서 발견)**: 당초 `d_target = λ/20` 단독이었으나,
λ=3cm(§28.1 기준 2)에서 실측 S̄_MoM=0.1125로 기준 0.100±0.005를 벗어남 —
원인은 `λ/20`이 λ가 커질수록 절대 간격(λ=3cm→1.5mm)이 성겨져 §26.2 수렴
표(λ=1cm 기준)가 보증하는 수준의 정확도를 유지하지 못했기 때문. §26.2 표의
수렴 기준값(S̄=0.076→0.061, d=1mm→0.25mm으로 갈수록 하위헌스 값에 수렴)이
실제로는 `d≤1mm`에서 얻어진 것이었으므로, `λ/20`에 `1mm` 상한을 추가로 걸어
λ가 커져도 격자가 1mm보다 성겨지지 않게 정정했다. 정정 후 λ=3cm에서
S̄_MoM=0.09999로 기준을 충족(§28.1 각주 참고). λ=1cm(`λ/20=0.5mm<1mm`)
케이스는 이 정정으로 값이 바뀌지 않는다.

`N`이 400 상한에 걸려 실제 `d > 1.05·(λ/20)`(목표 대비 5% 초과)이 되면
지표 박스에 경고 배지를 띄운다(예: `⚠ N=400 상한, d=λ/14.2 (목표 λ/20
미달)`). **공차 1.05배가 필요한 이유**: 공차 없이 `d > λ/20`만 조건으로
쓰면 대표 프리셋인 "깊은 그림자"(H=200mm, λ=1cm)에서 `N=401`이 필요한데
상한 400에 막혀 `d=λ/19.95`(0.25% 미달)가 되어 검증 기준 시나리오에 늘
경고가 붙는 오탐이 생긴다 — 실질적 이산화 누설이 아닌 반올림 수준 미달은
경고 대상에서 제외한다.

### 26.2 근거 — 사전 수치 검증(수렴 데이터)

λ=1cm, H=200mm 조건에서 이산화 간격에 따른 S̄_MoM:

| 간격 기준 | d      | S̄_MoM | 비고 |
|-----------|--------|--------|------|
| λ/10      | 1.0mm  | 0.127  | 하위헌스(0.057) 대비 2배 이상 — 이산화 누설 |
| λ/20      | 0.5mm  | 0.076  | 채택 기준 |
| λ/40      | 0.25mm | 0.061  | 더 세밀해도 하위헌스 값에 수렴 중 |
| (하위헌스) | —      | 0.057  | 해석식(이산화 없음) |

기존 앱의 솔리드 모드 근사 기준(script.js:731, `computeSolidWireLayout`)은
`d ≤ 1mm` **고정값**이지 `λ/10` 공식이 아니다 — 우연히 λ=1cm일 때만
`1mm = λ/10`과 일치할 뿐, 다른 λ에서는 기준이 다르다(예: λ=10cm이면
`1mm = λ/100`으로 오히려 더 세밀, λ=30cm에서도 여전히 `1mm` 고정). 표의
`d=λ/10` 행은 순수히 "λ에 비례한 상대 기준으로 얼마나 성긴지" 보여주기
위한 수치 검증용 비교점이며, 기존 앱이 실제로 그 공식을 쓴다는 뜻은
아니다. 어느 쪽이든 도선 사이 틈으로 새는 에너지가 회절로 위장해 비교
목적에는 부족하다 — 이것이 비교 페이지가 별도로 더 세밀한 `d=λ/20` 목표와
`N` 상한 400(기존 120 대비)을 쓰는 이유다.

증거(두 모형의 첫 밝은 무늬 겹침)이므로, 화면에서 직접 보여야 한다고
판단해 `±2.0·(H/2)`로 확대했다(241점 유지). 확대 후 H=200mm에서 화면 범위가
±200mm가 되어 y≈164~166mm의 첫 무늬가 정상적으로 표시됨을 스크린샷으로
확인.

### 27.3 프리셋 (사용자 확정)

프리셋 3개는 **같은 기하 조건(H=200mm, L=300mm)에서 λ만 바꾼 통제 실험
세트**이자 §28 acceptance 기준값의 재현 버튼이다 — H/L이 검증 조건과
달라지면 안 되므로 셋 다 H/L을 200mm/300mm로 고정한다:

- "깊은 그림자": H=200mm, L=300mm, λ=1cm
- "전이": H=200mm, L=300mm, λ=4cm
- "그림자 메워짐": H=200mm, L=300mm, λ=20cm

프리셋 클릭 시 `state.H_mm`/`L_mm`/`lam_cm`을 갱신한 뒤, `huygens/script.js`의
`setSlidersFromState()` 패턴과 동일하게 슬라이더 `value`와 라벨(`valbox`
텍스트)도 함께 동기화하는 `setSlidersFromState()`를 호출한다 — 슬라이더
핸들 위치나 표시 숫자가 프리셋 값과 어긋나지 않게 한다.

### 27.4 상태/계산 흐름

- H/L/λ 슬라이더 입력 → 200ms 디바운스 → **MoM과 하위헌스 두 곡선을 같은
  시점에 함께** 재계산(`recomputeMoM()` + 하위헌스 해석식 재평가) → 241점
  스크린 곡선·지표 박스 동시 갱신. 하위헌스는 해석식이라 그 자체로는
  즉시 계산 가능하지만, **MoM의 디바운스와 별도로 먼저 갱신하지 않는다**
  — 비교 페이지의 목적이 두 곡선의 정량 비교이므로, 슬라이더 드래그
  중 두 곡선이 서로 다른 파라미터 값으로 잠깐이라도 따로 그려지면(하나는
  최신 λ, 하나는 이전 λ) 비교가 무의미해진다. 두 모형 모두 같은 디바운스
  타이머 콜백 안에서 갱신한다.
- λ스윕: λ=1~30cm 로그 간격 10점을 `async` 루프로 순회하며 각 점마다 한
  프레임 양보(`requestAnimationFrame` 또는 `setTimeout(0)`)해 진행률
  텍스트를 갱신 — UI가 멈추지 않게 한다. 완료 후 진행률 패널을 S̄ vs λ
  꺾은선 차트로 교체.

### 27.5 지표 박스

- `N_F = (H/2)²/(λL)` 표시 + 각주: "하위헌스 앱 화면의 `a²/(λz)`는 이 값의
  4배"(하위헌스의 `a`는 전체 폭이라 `a²/(λz) = H²/(λL) = 4·N_F`).
- `I₀`(두 모형, y=0 지점), `S̄`(두 모형, `|y|≤H/2` 중점 100점 평균 —
  script.js의 `computeShadowFillRatio` 로직 재사용), 두 S̄의 상대 차이(%).
- 이산화 경고 배지(§26.1).
- **근축 유효 범위 힌트 문구**(지표 박스 아래 또는 페이지 하단 힌트 영역에
  상시 표시): "L이 H/2 수준이거나 작으면(광각) 하위헌스의 프레넬 근사가
  무너져 두 곡선이 크게 갈라집니다 — 근사 유효 범위의 시연이지 버그가
  아닙니다." L 슬라이더 범위(30~300mm)와 H 슬라이더 범위(20~300mm)가
  겹치므로 사용자가 L을 H/2 근방까지 내리는 조합을 쉽게 만들 수 있어,
  이 조합에서 두 곡선이 크게 벌어지는 것을 버그로 오인하지 않도록 상시
  노출한다.

## 28. 검증 계획

### 28.1 acceptance criteria (H=200mm, L=300mm 기준)

1. λ=2cm: 그림자 가장자리 바깥 첫 밝은 무늬가 **두 모형 모두 y=160~170mm
   구간에 있고, 두 모형의 위치 차이 ≤3mm, 세기 1.35~1.55, 세기 차이
   ≤0.08**(물리적 핵심은 두 모형이 상호 일치한다는 것).
2. λ=3cm: S̄ 두 모형 모두 0.100±0.005(전이 영역 정합).
3. λ=30cm: S̄_MoM ≈ 0.22, S̄_Huygens ≈ 0.33(하위헌스가 높음 — 키르히호프의
   회절 과대평가, 예측된 물리적 차이이지 버그가 아님).
4. λ=1cm: S̄_MoM이 d=λ/20 기준 0.08 이하(0.12 이상이면 이산화 누설 의심 —
   §26 d 산정 로직 점검).
5. 기존 `index.html`/`script.js`/`style.css`/`huygens/*`의 내용 무변경 확인
   (git diff로).

**정정 이력(구현 후 재검증에서 두 기준값 자체의 결함 발견, 코드 결함
아님)**:

- **기준 1**: 당초 "y≈160mm(±3mm), 세기 1.3~1.4"였으나, 실측값(MoM
  y=164.05mm/I=1.4376, Huygens y=165.65mm/I=1.4805)이 근소하게 벗어났다.
  원인은 기준값을 생성한 사전 스크립트의 봉우리 탐색 창이 `y=H/2+60mm`
  (=160mm)에서 잘려 있었던 것 — 두 모형이 우연히 똑같이 창 경계값
  159.8mm를 반환했던 것이 그 증거다. 실측 164.05mm/165.65mm가 참값이며,
  기준을 "두 모형 모두 y=160~170mm 구간, 위치 차이 ≤3mm, 세기 1.35~1.55,
  세기 차이 ≤0.08"로 교체했다(위 1번 항목에 반영). 아울러 x축 범위를
  §27.2에서 `±2.0·(H/2)`로 확대해 이 기준점이 메인 플롯 화면에서 직접
  보이도록 했다.
- **기준 2**: 당초 값 0.100은 사전 검증 시 `d=1mm`(λ=3cm 기준 λ/30에 해당)
  수렴 조건에서 실측한 것인데, §26.1 구현 사양은 `d_target=λ/20`이었다
  (λ=3cm→1.5mm, 잔여 이산화 누설 ~12%로 S̄_MoM=0.1125가 나옴). §26.1을
  `d_target = min(1mm, λ/20)`으로 정정해 재검증한 결과 S̄_MoM=0.09999로
  기준(0.100±0.005)을 충족했다. λ=1cm(기준 4)는 `λ/20=0.5mm<1mm`라 이
  정정으로 값이 바뀌지 않음(재확인 완료, 변화 없음).

### 28.2 추가 검증

- N=400(λ=1cm, H=300mm 근방) 케이스의 recompute 소요 시간을 콘솔에 로그

## 30. 회절 시뮬레이션 통합 허브(hub.html) — 배경과 목표

기존 세 화면(금속 막대, 하위헌스, 정량 비교)은 각각 따로 열어야 했다.
"직접 조작하며 비교"가 학습 목표이므로, 하나의 허브에서 두 시뮬레이션의
스크린 무늬를 개별로도, 나란히도, 정량 곡선으로도 볼 수 있게 한다.
기존 세 앱의 물리 코어·렌더링은 절대 건드리지 않고, 각 앱에 URL 파라미터
초기화만 최소 침습으로 추가한 뒤 iframe으로 조합한다.

### 30.1 URL 파라미터 사양

각 앱은 `applyUrlParams()` 함수 하나만 추가되며, 기존 함수는 무수정이다.
파라미터가 없으면 상태값이 HTML 슬라이더 기본값과 동일해 100% 기존
동작과 같다(회귀 없음, §28 acceptance 5 확장 적용·Playwright로 재검증
완료 — §30.6).

| 앱 | 파라미터 | 의미 | 반영 위치 |
|---|---|---|---|
| 금속(`index.html`) | `mode=solid` | 솔리드 막대 모드로 전환 | `state.mode` |
| | `H` (mm) | 장애물 높이 | `state.H_mm` + `hSlider.value` |
| | `L` (mm) | 스크린 거리 | `state.L_mm` + `lSlider.value` |
| | `lam` (cm) | 파장 | `state.lam_cm` + `lamSlider.value` |
| 하위헌스(`huygens/index.html`) | `lambda` (m) | 파장 | `state.lambda`(RANGES로 클램프) |
| | `a` (m) | 장애물 폭 | `state.a`(RANGES로 클램프) |
| | `z` (m) | 장애물–스크린 거리 | `state.z`(RANGES로 클램프) |
| 비교(`compare.html`) | `H`(mm)/`L`(mm)/`lam`(cm) | 금속과 동일 | `state.H_mm`/`L_mm`/`lam_cm` |

호출 위치: 금속·비교는 각 파일의 "시작" 블록 맨 앞, 하위헌스는 `init()`의
맨 앞. 세 파일 모두 함수 정의는 기존 마지막 함수 바로 뒤에 추가했다
(script.js: `selfCheck()` 뒤, huygens/script.js·compare.js:
`setSlidersFromState()` 뒤).

### 30.2 iframe 상주 + CSS 전환 (재배치·복제 금지)

**결정**: iframe은 금속·하위헌스·비교 3개만 생성하고 페이지 수명 내내
DOM에 상주시킨다. 탭 전환은 CSS(위치·크기·visibility)만 바꾼다.

**근거**: iframe을 탭마다 새로 만들거나 다른 컨테이너로 옮기면(재배치·
복제) 브라우저가 iframe을 다시 로드한다 — 그러면 사용자가 개별 화면에서
조작한 상태(줌, 재생/일시정지, 위상, 드래그한 관측점 등)가 탭을 오갈
때마다 사라진다. 상주 방식만이 "각 화면을 따로 조작하며 비교"라는 목표를
지킨다.

**`display:none` 함정과 해결**: 숨김 처리를 `display:none`으로 하면 그
컨테이너는 렌더 트리에서 완전히 빠져 `clientWidth/Height`가 0이 되고,
내부 iframe의 캔버스도 리사이즈 로직에 의해 0×0으로 줄어든다. 이후 다시
보이게 해도(`display: block`으로 복귀) 캔버스가 스스로 원래 크기를
되찾지 못해 빈 화면이 된다(리사이즈 이벤트가 없으면 캔버스 크기 갱신
로직이 다시 실행되지 않으므로).

해결: 숨기는 쪽은 `position:absolute`로 flex 흐름에서 빼되(형제가
`flex:1 1 100%`로 전체를 차지할 수 있게), 숨기기 직전 컨테이너의
실측 `clientWidth/clientHeight`를 그대로 내려받아 **명시적 px 크기**를
유지하고 `visibility:hidden`만 추가한다. 즉 "화면에는 없지만 크기는 0이
아닌" 상태로 만들어, 내부 iframe 문서가 한 번도 0×0 뷰포트를 보지 않게
한다(따라서 애초에 되찾을 필요가 없다). 사용자가 애초에 제시한 대안
2안("visibility:hidden + width:0" 또는 "absolute로 화면 밖")을 절충한
형태로, off-screen 이동은 필요 없었다 — `visibility:hidden` 자체가 이미
페인트·히트테스트를 제거하므로 위치를 뷰포트 밖으로 옮기지 않아도 된다.

**리사이즈 전달**: 탭을 바꿔 크기가 달라진 iframe에는
`requestAnimationFrame` 한 프레임 뒤 `contentWindow.dispatchEvent(new
Event('resize'))`를 보낸다(동일 출처 `file://`라 접근 가능). 크로스오리진
예외 대비로 `try/catch`로 감쌌다.

### 30.3 단위 환산표

마스터 컨트롤은 금속·비교 앱과 같은 단위(mm, cm)를 쓰지만 하위헌스는
SI(m)를 쓴다. 허브에서 iframe을 리로드할 때 다음 표대로 환산한다
(`hub.js`의 `reloadAll()`):

| 마스터 파라미터 | 금속(`index.html`) | 하위헌스(`huygens`) | 비교(`compare.html`) |
|---|---|---|---|
| `H_mm` (mm) | `H=H_mm` (mm 그대로) | `a=H_mm/1000` (m) | `H=H_mm` (mm 그대로) |
| `L_mm` (mm) | `L=L_mm` (mm 그대로) | `z=L_mm/1000` (m) | `L=L_mm` (mm 그대로) |
| `lam_cm` (cm) | `lam=lam_cm` (cm 그대로) | `lambda=lam_cm/100` (m) | `lam=lam_cm` (cm 그대로) |

조건 대응 안내(마스터 컨트롤 바 하단 고정 문구): "하위헌스 화면의
a²/(λz)는 금속 앱 N_F의 4배" — 하위헌스의 `a`는 금속의 전체 높이 `H`에
대응하므로(반높이가 아님) 프레넬 수 정의(§25 참조, 하위헌스 쪽은
반폭²/λz, 금속 N_F는 반높이²/λz 계열)의 배율 차이를 상기시키는 힌트다.

### 30.4 탭 순서 및 초기 상태(사용자 확정)

탭 순서는 **①하위헌스 ②금속 막대 ③나란히 보기 ④정량 비교**이며, 허브의
초기 활성 탭은 ①이다. ③ 나란히 보기의 좌우 배치도 **좌=하위헌스,
우=금속**으로 통일했다(탭①→③→②로 이동해도 하위헌스가 항상 화면
왼쪽에 있어 시선 이동이 최소화된다). DOM 순서 자체를 하위헌스 wrap →
금속 wrap 순으로 작성해 별도 `order` 스타일 없이 flex 기본 순서로
좌우 배치가 결정되게 했다(§30.2의 "재배치 금지" 원칙과 일관 — 이 순서는
런타임에 바뀌지 않는 최초 마크업 결정이다).

초기값은 "전이"(H=200mm·L=300mm·λ=4cm) 조건이다. 세 프리셋(깊은 그림자
λ=1cm / 전이 λ=4cm / 그림자 메워짐 λ=20cm) 중 두 모형이 부분적으로
갈라지기 시작하는 전이 구간이 처음 보여주기에 가장 흥미로운 조건이라고
판단했다(§28.1 기준 2 참조 — 두 모형이 정합하면서도 회절 전이가 관찰되는
지점).

### 30.7 ③ 나란히 보기 — 하위헌스 그래프 패널 먼저 보이기

**문제**: `huygens/style.css`의 980px 이하 미디어 쿼리가 절반 폭(③)에서
세로 스택 레이아웃을 발동시켜, 헤더·슬라이더가 먼저 보이고 ①번 그래프
패널(`#panel-main`)은 스크롤해야 보였다.

**실측으로 뒤집힌 전제**: 처음 제안된 해법은 "같은 출처(`file://`)이므로
허브에서 `iframe.contentDocument`에 직접 접근해 스크롤한다"였다. 그러나
실측 결과 Chrome은 `file://` 문서를 **파일마다 서로 다른 불투명(opaque)
출처**로 취급한다(같은 폴더에 있어도 예외 없음):

| 접근 | 결과 |
|---|---|
| `iframe.contentDocument` | `null`(예외 없이 조용히 실패) |
| `iframe.contentWindow.dispatchEvent(...)` | `SecurityError` |
| `iframe.contentWindow.location.href` | `SecurityError` |
| `iframe.contentWindow.postMessage(...)` | **성공**(opaque 출처 간에도 예외적으로 허용되는 API) |

부수 발견: §30.2의 `dispatchResize()`(탭 전환 시 `contentWindow.dispatchEvent`
로 리사이즈 이벤트 전달)도 같은 이유로 **애초부터 계속 실패해 왔다**. 다만
이건 실질적 문제가 아니었는데, 브라우저가 iframe의 CSS 크기가 바뀔 때
그 내부 문서에 **네이티브 resize 이벤트를 자동으로 보내주기 때문**이다
(수동 전달이 애초에 불필요했다). `dispatchResize()`는 그대로 남겨뒀다 —
실패해도 무해하고(try-catch), 코드를 지우는 것은 이번 작업 범위 밖이다.

**검토한 대안과 기각 이유**:
1. **URL 해시(`#panel-main`) + ③ 최초 진입 시 강제 리로드**: 브라우저가
   해시로 네비게이션 시점에 자동 스크롤해주는 표준 기능을 이용 — huygens
   무수정으로 가능했다. 하지만 초기 로드가 항상 ①(전체 폭, 스택 안 됨)에서
   일어나므로, 나중에 ③으로 처음 전환될 때 그 시점의 레이아웃(스택됨)
   기준으로 해시를 다시 계산시키려면 하위헌스 iframe을 한 번 더 리로드해야
   했다. 이는 §30.2의 "탭 전환은 iframe을 리로드하지 않는다" 불변식을 깨고,
   사용자가 ①에서 미리 조작해 둔 상태(드래그한 관측점, 슬라이더 등)를
   파괴한다 — 사용자가 이 트레이드오프를 명시적으로 거부해 기각.
2. **postMessage(채택)**: 리로드가 전혀 필요 없다. opaque 출처 간에도
   항상 허용되는 예외적 API라 안전하게 전달된다. 대가는 `huygens/script.js`
   에 최소 리스너(방어적 조건 검사 + try-catch, 메시지가 없으면 완전히
   기존 동작과 동일) 4~5줄을 추가하는 것 — 사용자가 이 트레이드오프를
   명시적으로 승인했다.

**구현**: `hub.js`에 `needsScrollHuygens` 플래그(§30.2의 리사이즈 로직과
같은 패턴) — 하위헌스 iframe의 `load` 이벤트마다 켜지고, ③ 활성 상태에서만
`postMessage("scrollToPanelMain", "*")`를 보낸 뒤 꺼진다. 플래그가 꺼져
있으면 아무 것도 하지 않으므로, 사용자가 ③에서 직접 스크롤한 위치를 다른
탭을 거쳐 돌아와도 되돌리지 않는다. `huygens/script.js`는
`window.addEventListener('message', ...)`로 정확히 문자열
`'scrollToPanelMain'`만 반응하고, 그 외 메시지·예외는 조용히 무시한다.

**검증 중 발견한 별개 성능 특성(참고용, 이번 작업 범위 밖)**: 금속 앱의
MoM 재계산(`recompute()`)이 그리드 해상도가 커진 상태(`gridH` 수백~900대)
에서 리로드당 수 초~수십 초가 걸릴 수 있고, 이는 (동일 `file://` 사이트로
묶여 한 렌더러 프로세스/스레드를 공유하는 것으로 추정되는) 세 iframe이
같은 스레드를 공유해 하위헌스의 스크립트 실행·메시지 수신까지 지연시킨다.
실측: `[적용]`/프리셋으로 세 iframe을 동시 리로드한 뒤 하위헌스 문서가
완전히 로드되고(`readyState=complete`) 스크롤이 정확히 반영되기까지 약
47초가 걸린 사례를 관찰했다(재현: 시뮬레이션 상호작용을 여러 번 거쳐
`gridH`가 커진 상태에서 프리셋 클릭). postMessage 자체는 즉시 전달되고
정확히 동작하지만, **수신 측(하위헌스) 스크립트가 실행을 마칠 때까지
막혀 있으면 그만큼 늦게 반응한다** — 버그가 아니라 금속 앱의 기존 계산
비용이 그대로 드러난 것이다. 이번 작업 범위가 아니므로 손대지 않았지만,
허브의 체감 반응성에 영향을 주는 사항이라 기록해 둔다.

**검증 결과**: ①에서 바로 ③ 진입 시 스크롤 정상(`top≈0`,
`scrollY=1062`), ③ 활성 중 프리셋 클릭 → 리로드 후에도 스크롤 정상
(격리된 단일 리로드 테스트로 즉시 확인, 전체 리로드 시나리오는 타임스탬프
추적으로 47초 시점 완료 확인), ③에서 수동 스크롤 후 ④→③ 복귀 시 위치
유지(재스크롤 없음) 확인. 기존 25건 회귀(huygens 단독 실행 포함)도 모두
통과 — 메시지 리스너는 메시지가 없으면 완전히 무동작이라 기존 동작에
영향 없음. `git diff`는 `hub.js`(§30.7 로직 추가분)와
`huygens/script.js`(리스너 4~5줄 추가분)만 포함.

### 30.8 마스터 컨트롤 라이브 동기화 — 리로드 제거 + lockScale 파라미터

**배경**: §30.5의 [양쪽에 적용]/프리셋은 iframe 3개 전체 `reloadAll()`이라 (1) 리로드
오버헤드로 체감 지연이 크고 (2) 각 앱의 조작 상태(줌, 관측점 드래그, 스케일 고정 등
파라미터 외 상태)를 매번 파괴했다.

**해결**: §30.7에서 도입한 postMessage 채널을 확장해 `{ type: 'diffhub-setParams',
H_mm, L_mm, lam_cm }` 메시지를 추가했다. 세 앱은 각자 기존 슬라이더 input 핸들러가
쓰는 상태 갱신 + 슬라이더/라벨 동기화 + 디바운스 recompute 경로를 그대로 재사용한다
(새 계산 경로 없음 — 슬라이더로 직접 조작한 것과 동일한 코드 경로).

- 마스터 슬라이더 input → 300ms 디바운스 후 setParams 전송(hub.js `scheduleParamSync`).
  금속 앱의 recompute(~1~2초)는 물리 계산 자체의 비용이라 그대로 수용한다 —
  제거 대상은 리로드 오버헤드뿐이다.
- 프리셋 버튼 → 상태 갱신 + 마스터 슬라이더 동기화 + 대기 중인 디바운스를 취소하고
  즉시 setParams 전송(리로드 없음).
- [양쪽에 적용]은 `↺ 전체 초기화`로 이름을 바꿔 기존 `reloadAll()`을 그대로
  유지한다 — 앱이 이상 상태에 빠졌을 때의 수동 탈출구.

**메시지 사양**:
```
{ type: 'diffhub-setParams', H_mm: number, L_mm: number, lam_cm: number }
```
`type`이 정확히 일치하지 않으면 무시한다. 세 앱 모두 전체 `try/catch`로 감싸
처리 실패가 콘솔 에러로 새지 않게 했다.

**lockScale 파라미터**: 하위헌스 앱의 "화면 스케일 고정" 체크박스를 URL로 초기
켜짐 상태로 만들기 위해 `applyUrlParams()`가 `lockScale=1`을 읽어 반환하고,
`init()`이 초기 렌더(첫 `recomputeAll()`) 직후 체크박스를 프로그램적으로 켜서
기존 `change` 핸들러(스케일 고정 스냅샷 로직)를 그대로 재사용한다. 파라미터가
없으면 `false`를 반환하므로 단독 실행 시 기존 동작과 100% 동일하다. 허브의
하위헌스 iframe은 초기 src와 `↺ 전체 초기화`가 만드는 src 모두에 `&lockScale=1`을
붙여, 허브 안에서는 항상 스케일 고정이 기본 켜짐 상태를 유지하게 했다(프리셋으로
λ를 바꿔도 Y축 범위가 고정되어 무늬 퍼짐을 같은 자로 비교할 수 있다).
